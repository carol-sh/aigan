# v4 이용 시나리오 4: 의심하고 평가하는 Agent

지금까지의 시나리오는 "했냐 안 했냐"를 다뤘다. 이 시나리오는 "잘했냐"를 다룬다. Agent는 사용자의 보고를 그대로 믿지 않고, 결과의 질을 평가하고, 허투루 했으면 혼낸다. 판단은 전부 LLM이 한다.

이 문서는 프롬프트 본문(설계 §10의 6번)을 쓸 때 기준 장면으로 쓴다. 사용자가 원하는 Agent상은 다음과 같다.

> 내가 일을 허투루 하면 좀 혼쭐 내줄 에이전트. 내가 진짜 잘 했는지 의심하고 관리해 주면 최고.

## 설정

| 항목 | 값 |
|---|---|
| 방침 | 자기계발: 알고리즘 문제 풀이 |
| 프롬프트 성향 | 매우 pushy. 이어가기 1–5분. 결과보다 이유를 묻는다. 미달이면 재촉한다. 답이나 힌트를 주지 않는다(E4) |
| 목표 | "AtCoder C 한 문제 AC". 완료 조건: AC 제출 결과 보고 |
| 서브태스크 | 시작할 때 진행 메모에 계획. ① 문제 가져오기 ② 핵심 아이디어 ③ 복잡도 ④ 구현·제출 |

Agent는 문제를 직접 볼 수 없으므로 문제를 가져오는 것부터 사용자의 일이다(역전 검토의 "사람은 Agent의 눈과 손"). 문제는 ABC C 수준의 전형 문제를 가정했고 특정 회차를 가리키지 않는다. 사용자 메시지에 대한 응답은 디바운스(20초) 뒤에 나가지만 아래 시각은 분 단위로 줄였다.

## 흐름 1: 문제 가져오기

```
21:00  [개시 예약 발화, intent "자기계발: 알고리즘 한 문제"]
21:00  Agent: 노트북 켜. 오늘은 AtCoder 한 문제 푼다.
              ① 최근 ABC에서 C번 하나 골라서 문제 요약이랑 제약 조건 붙여 넣어. 5분.
       [goal_create("AtCoder C 한 문제 AC", 완료 조건: AC 제출 결과 보고)]
       [goal_update(progress: "① 문제 가져오기 - 진행 중 / ② 핵심 아이디어 / ③ 복잡도 / ④ 구현·제출")]
       [continue 21:05]

21:04  나: 길이 N인 정수 수열 A가 있고, 합이 K인 연속 부분 수열 개수를 세는 문제.
           N ≤ 2×10^5, |A_i| ≤ 10^9
21:04  Agent: 좋아. 코드 치지 마. ② 핵심 아이디어부터 한두 줄로 말해.
       [goal_update(progress: "① 완료(연속 부분합 = K 개수, N≤2e5, 음수 있음) / ② 진행 중 …")]
       [continue 21:09]
```

## 평가 1: 했지만 틀린 답

```
21:07  나: 시작점이랑 끝점 이중 for문 돌면서 합 세면 됨
21:07  Agent: 반려. N이 2×10^5면 쌍이 2×10^10개야. 2초 안에 안 끝나.
              N 제약을 보고 나서 아이디어를 내. 다시.
       [goal_update(progress: "… ② 1차 O(N²) 반려(제약 무시) …")]
       [continue 21:10]

21:09  나: 투 포인터?
21:09  Agent: 반려. 투 포인터가 되려면 뭐가 성립해야 하는지 말해 봐. 그리고 그게 이 문제에서 성립하는지.
       [continue 21:11]

21:11  Agent: 대답.
21:12  나: 오른쪽 늘리면 합이 커져야 하는데... 음수가 있어서 안 되네
21:12  Agent: 그래. 근거 없이 이름만 던지지 마. 다른 아이디어. 3분.
       [goal_update(progress: "… ② 2차 투 포인터 반려(음수로 단조성 깨짐, 본인이 확인) …")]
       [continue 21:15]

21:15  Agent: 3분 지났다. 아이디어.
21:16  Agent: 생각 중이면 생각 중이라고라도 해.
21:17  나: 생각 중
21:17  Agent: 2분 더.
       [continue 21:19]
21:18  나: 누적합 S로 쓰면 S[r] − S[l] = K니까, S[r] − K인 S[l] 개수를 세면 됨.
           앞에서부터 누적합 개수를 맵에 쌓으면서
21:18  Agent: 통과. ③ 시간 복잡도는?
21:19  나: O(N log N)? 맵이니까
21:19  Agent: 맞아. 해시맵이면 평균 O(N). 어느 쪽이든 2×10^5면 충분해. ④ 구현해서 제출해. 15분.
       [goal_update(progress: "① 완료 / ② 3차 누적합+맵 통과(힌트 없음, 12분) / ③ 통과 / ④ 진행 중")]
       [continue 21:34]
```

결과가 맞는지만 보지 않고 이유를 말하는지를 본다. 반려할 때 답을 알려 주지 않는다. 왜 틀렸는지는 사용자가 말하게 하고, 막히면 재촉한다.

## 평가 2: 제출했지만 틀림

```
21:34  Agent: 제출했어? 결과.
21:35  나: WA 3개 나옴
21:35  Agent: 틀린 데가 있어. 어딘지는 안 알려 준다. 5분 안에 찾아.
       [goal_update(progress: "… ④ 1차 WA …")]
       [continue 21:40]

21:38  Agent: 2분 남았다.
21:40  Agent: 찾았어?
21:40  나: 아 맵에 0 안 넣었다. 처음부터 r까지 구간을 못 셈
21:40  Agent: 그거 하나야? 정답이 최대 얼마까지 커지는지 계산해 봤어?
21:42  나: N(N+1)/2니까 2×10^10... int 넘네. long long으로 바꿈
21:42  Agent: 둘 다 고쳐서 다시 내.
       [continue 21:47]

21:45  나: AC!
21:45  Agent: 왜 0을 넣어야 했는지 한 줄로 설명해 봐.
21:46  나: 처음부터 r까지의 구간도 세려면 l=0일 때 S[0]=0이 있어야 해서
21:46  Agent: 정확해. 오늘 놓친 건 둘이야. 제약 보고 복잡도부터 잡기, 경계값과 답의 범위.
       [goal_close(done, "AC. 아이디어 3차 통과, WA 1회(S[0] 초기값·오버플로, 본인이 찾음)")]
       [end → 정리 호출]
```

AC 보고만으로 닫지 않는다. 핵심을 이해했는지 한 번 더 확인한 뒤에 닫는다. 버그도 Agent가 짚지 않고, 사용자가 찾게 한 뒤 질문으로 더 파고든다.

## 다른 결말: 해설 의존으로 실패

```
21:34  Agent: 제출했어? 결과.
21:35  나: WA. 모르겠다 그냥 해설 볼래
21:35  Agent: 해설 보는 건 막지 않는다. 대신 해설 닫고, 왜 틀렸는지 네 말로 설명해. 10분.
       [continue 21:45]
21:45  Agent: 설명.
21:48  나: 해설에 누적합 0 넣으래서 넣었더니 됨
21:48  Agent: 그건 따라 한 거지 이해한 게 아니야. 오늘 문제는 실패로 친다.
              내일 같은 유형으로 하나 더 한다.
       [goal_close(failed, "해설 의존. S[0] 초기값 이유 설명 못 함")]
       [open_reserve(내일 21:00, intent "누적합 + 맵 유형 재도전")]
       [end]
```

AC를 받았어도 실패로 판정한다. 완료 조건은 "AC 보고"였지만, 평가는 그 위에서 LLM이 내린다.

## 하네스와 Agent의 몫

| 장면 | 하네스 | Agent(LLM) |
|---|---|---|
| 문제 가져오기 | 텍스트 메시지 수신 | 무엇을 가져올지 지시 |
| 아이디어 평가 | 없음 | 제약을 보고 반려·통과, 틀린 이유를 사용자가 말하게 함 |
| 코드 평가 | 텍스트 수신(코드도 텍스트) | 틀렸다는 판정만. 위치는 사용자가 찾게 함 |
| 막힘 | 이어가기 재발화 | 재촉 간격, 말투 |
| 이해 확인 | 없음 | 설명을 시키고 판정 |
| 완료 판정 | `goal_close` 결과 반영 | done/failed, 사유 |
| 평가 이력 | 진행 메모·종료 사유 저장 | 반려 사유, 스스로 찾았는지 기록 |

하네스에 새로 필요한 장치는 없다.

## 일반화: 의심하는 Agent

AtCoder는 예시일 뿐이고, 사용자가 원하는 것은 모든 방침에서 "진짜 잘했는지 의심하고 관리"하는 Agent다. 이 시나리오에서 나온 기법을 다른 방침에도 쓸 수 있게 정리한다. 모두 프롬프트(턴 규칙의 공통부)에 들어갈 내용이다.

| 기법 | 이 시나리오 | 다른 방침의 예 |
|---|---|---|
| 결과 대신 이유를 묻는다 | "왜 0을 넣어야 했는지 설명해" | 영어 단어: 뜻 말고 예문을 만들게 함 |
| 구체적 세부를 묻는다 | "정답이 최대 얼마까지 커져?" | 운동: "마지막 세트 몇 개였어?" / 독서: "그 장에서 제일 이상했던 주장은?" |
| 보고와 앞선 진술의 모순을 본다 | 해설을 따라 한 것과 이해한 것을 구분 | "아까 회의 중이라며 언제 30분 걸었어?" |
| 미달이면 재촉한다. 답을 주지 않는다 | "틀린 데가 있어. 어딘지는 안 알려 준다" | 글쓰기: 고쳐 주지 않고 "이 문단 다시" |
| 기준을 미리 말한다 | "N 제약 보고 나서 아이디어 내" | "세 줄 일기, 사실 말고 느낀 것 한 줄 포함" |
| 다음 날 재검증한다 | 같은 유형 재도전 예약 | 어제 외운 단어 다시 묻기 |

한계:

- **현실은 검증할 수 없다.** Agent는 보고만 받는다. 위 기법들은 거짓 보고를 막지 못한다. 꾸며 내는 비용을 높이고, 대충 한 결과를 드러낼 뿐이다. 증거 첨부(사진, 제출 결과 화면)는 1차 범위 밖이다(설계 §7, 역전 검토 K3).
- **LLM의 평가도 틀릴 수 있다.** 이 시나리오처럼 판정이 명확한 영역(알고리즘)과 달리, 글쓰기·판단 같은 영역은 기준이 흐리다. 사용자가 반박하면 Agent가 근거를 들어 다시 판정하게 하는 것은 프롬프트의 몫이다.

## 발견한 것

| # | 내용 | 처리 |
|---|---|---|
| E1 | 혼쭐이 먹히려면 패턴을 짚어야 한다("지난주에도 제약 안 보고 이중 for문 냈지"). 지금은 목표의 종료 사유 한 줄만 남아, 같은 실수가 반복돼도 Agent가 모른다 | memory 설계의 출발 질문으로 삼는다: 사용자의 약점·반복 실수를 어떻게 쌓고 다시 꺼내 쓰나. K1(사람이 만든 결과물 보관)과 같은 축 |
| E2 | "의심하는 태도"는 방침마다 다시 쓰지 않고 턴 규칙의 공통부에 둔다. 방침 본문은 그 영역의 평가 기준만 준다(알고리즘: 제약·복잡도·이해) | 프롬프트 본문 작성 때 반영 |
| E3 | 완료 조건(`done_criteria`)은 최소 기준이고, 판정은 그 위에서 LLM이 한다(AC인데 failed) | 하네스 변경 없음. `goal_close` 사유에 판정 근거를 남기게 한다 |
| E4 | 사용자의 이전 실험: "미달이면 단계를 쪼갠다"를 프롬프트에 넣으면 Agent가 결국 답을 알려 주고 그대로 쓰라고 하는 식으로 무너진다. 재촉이 낫다 | 턴 규칙 공통부: 미달이면 재촉하고, 답·힌트·더 쉬운 단계를 주지 않는다. 막힌 지점은 질문으로 사용자가 말하게 한다. 단계 계획은 목표를 만들 때 한 번 하고, 미달을 이유로 다시 쪼개지 않는다 |
