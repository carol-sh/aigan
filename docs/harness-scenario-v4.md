# v4 이용 시나리오: 하루 추적

실행 모델(§4.5)과 처리 순서(§4.2)를 하루치 사용에 대입해서, 루프가 실제로 무엇을 하는지 따라가고 허점을 찾는다.

## 설정

| 항목 | 값 |
|---|---|
| 방침 | `health`: 건강한 생활 시키기(물, 스트레칭, 산책) · `work`: 업무 보고 받기(오전 지시, 중간·최종 보고) |
| 블랙아웃 | 01:00–08:00. 계획일은 08:00에 시작 |
| 디바운스 | 20초 |

표기: 루프 단계는 §4.5 번호(1 고르기, 2 읽기, 3 LLM, 4 커밋, 5 전송, 6 후속). `R`은 개시 예약, `G`는 목표, `F`는 흐름.

## 발견한 허점

H2–H6은 제안대로 설계 문서에 반영했다.

| # | 허점 | 영향 | 제안 |
|---|---|---|---|
| H1 | 흐름 길이 상한이 없음(§7 미정 항목) | 무응답 흐름 하나가 다른 모든 개입을 밤새 막을 수 있다 | **결정**: 하네스 상한을 두지 않는다. 포기·종료는 LLM이 정한다. 대신 H2로 밀린 개입을 모든 턴에 보여주고, 블랙아웃 무응답 닫기가 하루 단위 상한이 된다 |
| H2 | 진행 중 흐름의 턴이 밀린(`fired`) 개시 예약을 모름 | 마감 확인이 흐름이 끝날 때까지 늦어진다 | 모든 턴의 이벤트 블록에 `fired` 목록을 넣는다. AI는 이번 흐름에서 다루고 `open_cancel`하거나, 흐름을 마무리할 수 있다 |
| H3 | 턴이 `scheduled` 개시 예약을 모름 | 사용자가 먼저 보고해도 예약을 취소 못 해 중복 질문이 생긴다. 목표가 닫힌 경우만 사전 검사가 구해준다 | 턴 입력의 활성 목표 옆에 그 목표에 걸린 예약(id, at, intent)을 붙인다 |
| H4 | 그림·§4.5의 "타이머 = 가장 이른 예약 1개"가 불완전 | 디바운스, 보류 해제, 정리 재시도, 계획 시점도 타이머가 깨워야 한다 | 타이머는 "다음 기한" 하나를 조준: `MIN(개시·이어가기 at, 디바운스 만료, hold_until, 정리 재시도, 계획 시점)` |
| H5 | 과거 시각 개시 예약 규칙 없음 | 늦은 계획·늦은 턴이 지난 시각을 예약할 때 동작 미정 | 저장 시 `at < now`면 `now`로 당긴다(블랙아웃이면 끝으로). 버리지 않는다 |
| H6 | 사용자 개시 턴에서 흐름을 언제 만드는지 불명확 | pre에서 흐름을 만들면 `respond=false` 롤백이 두 tx에 걸친다 | 흐름 생성은 커밋 tx에서만. pre는 읽기만 한다. `respond=false`면 커밋 tx가 메시지를 `ignored`로만 표시한다 |

## 확인된 것(허점 아님)

- 정리 중 도착한 메시지("고마워")는 `pending`으로 쌓였다가 판정되거나 다음 개시 턴에 흡수된다. 메시지가 사라지지 않는다.
- 전송이 커밋 직후 루프 안이라, 흐름의 마지막 메시지는 정리 전에 이미 나가 있다.
- 디바운스 대기 중 이어가기가 발화하면 이어가기 턴이 답하고, 뒤의 디바운스 만료는 무시된다(v3 추적 16과 같음).
- 블랙아웃 중 사용자가 연 흐름은 무응답이면 다음 이어가기에서 닫힌다.
