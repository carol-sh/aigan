# 3단계 구현 계획: LLM 실행기

## Context

2단계까지는 LLM 자리에 결정자(`TurnDecider`, `CleanupDecider`)가 있고, 테스트에서는 각본이 그 자리에서 도구를 직접 부른다. 그래서 다음은 아직 실제 코드가 아니다.
- 모델에 무엇을 보여 주는가(입력 조립, §5.1·§5.3)
- 모델의 답을 어떻게 읽는가(출력 스키마, 파싱 재시도, §5.4)
- 도구 라운드는 어떻게 도는가(라운드 상한, 강제 호출)
- 요청을 어떻게 기록하는가(`llm_calls`, `daily_calls`)
- 턴 io와 텔레그램이 어떻게 맞물리는가(입력 중 표시, io 중 도착 메시지 지우기, §2.5)

이번 단계는 결정자를 **LLM 실행기 + 입력 조립**으로 채운다. 테스트의 가짜 경계는 결정자에서 SDK 모양의 `ChatClient`로 내려간다(정본 §6.7). 각본은 이제 "모델"이 되어 completion을 낸다. 그러면 도구 라운드, 재시도, 기록, 입력 조립이 테스트에서도 실제 코드로 돈다. 2단계의 e2e는 각본 문법(`await`)만 바뀌고 기대값은 그대로라, 이번 단계의 회귀 테스트가 된다.

## 범위

**포함**
- 실행기(`src/llm/`):
  - 도구 라운드와 `max_tool_rounds`·`max_cleanup_tool_rounds` 상한. 넘으면 도구 목록은 둔 채 `tool_choice: "none"`으로 강제 호출한다.
  - 파싱·스키마 실패 시 1회 재시도.
  - 요청마다 `llm_calls` 한 행. `daily_calls`는 요청마다 1씩 늘리고, 날짜가 바뀌었으면 먼저 0으로 되돌린다.
  - `ToolBox` → OpenAI 함수 도구 정의(`z.toJSONSchema`).
- 출력 스키마: 턴(트리거별, 48h), 정리(JSON 객체면 된다).
- 입력 조립:
  - 턴(§5.1): 방침 목록, 활성 목표, 개시 예약 전체, 오늘 종료 목표, 오늘 계획, 직전 흐름 꼬리, 흐름 대화, 흐름 밖 메시지, 이벤트 블록, 기억.
  - 정리(§5.3): 기억, 흐름 정보, 목표, 대화 원문(무시됨 표시).
  - `upto`를 "입력에 넣은 user 메시지의 최대 id"로 바꾼다.
- 실제 결정자: `LlmTurnDecider`(되묻기는 같은 대화를 잇는다), `LlmCleanupDecider`.
- 텔레그램 쪽:
  - 흐름 안 턴의 입력 중 표시(12b).
  - 말한 턴의 io 중 도착 메시지 지우기와 `busy` 표시(12a, 12f, 12g, 31, 35, 44).
- 가짜: `ScriptedLlm`을 각본 모델(가짜 `ChatClient`)로 바꾸고 기존 e2e를 옮긴다.

**제외**
- 턴 실패 단계로:
  - 시도 선기록, `fail_turn`, `output_fail_*`, 포기, 운영자 알림.
  - 이번 단계에서 실패한 결정은 2단계처럼 경고만 남긴다. 실행기는 오류를 출력 실패와 API 실패로 나눠 던져, 다음 단계가 바로 쓰게 둔다.
- 게이트 단계로: 일일 상한·잔액 확인, 보류 진입(107, 110).
- 계획 단계로: 계획 입력·출력·커밋. 계획은 지금처럼 가짜 핸들러로 둔다.
- 압축 단계로:
  - `summary` 반영(흐름 대화, 정리의 90b).
  - 아직 요약을 만드는 코드가 없어 검증할 수 없는 분기라 이번에는 넣지 않는다.
- 어댑터 단계로: 실물 OpenAI 클라이언트(`createChatClient`), 수동 스모크, `main.ts`.

## 코드 작성 원칙 (이전 계획에서 이어짐)

사람이 읽기 쉬운 코드가 최우선이다. 주석을 많이 다는 것이나 빠르게 도는 것보다 앞선다.

- **이름만 보고 하는 일을 알 수 있게 한다.**
  - 함수는 동사구로 짓고, 반환값이나 효과를 이름에 드러낸다(`assembleTurnInput`, `renderTurnInput`, `deleteMessagesArrivedDuringIo`).
  - 정본의 약칭(`ctx`, `upto`, `io_from`, `judge`)을 그대로 옮기지 않는다. 하는 일을 말하는 이름으로 바꾼다(아래 표).
  - 불리언은 `is`/`has`로 시작하고, 시각 값은 `...At`으로 끝낸다.
- **주석은 이름과 구조로 설명할 수 없는 복잡한 로직에만 단다.** 이번 단계의 예:
  - 강제 호출에서도 `tools`를 빼지 않는 이유(캐시 prefix)
  - 직전 흐름 꼬리를 처리 시각이 아니라 메시지 시각으로 재는 이유
  - 지우기를 커밋 tx 밖에서 하는 이유(텔레그램 호출은 tx 안에 둘 수 없다)

  무엇을 하는지 되풀이하는 주석이나 절 번호만 적은 주석은 달지 않는다.
- **함수 하나는 한 단계의 추상만 다룬다.**
  - 실행기의 라운드 루프는 "보내기 → 도구면 실행하고 잇기 → 아니면 읽기 → 실패면 한 번 더"로 위에서 아래로 읽히게 쓴다.
  - 입력 조립은 절마다 이름 붙은 함수 하나(`findPreviousFlowTail`, `listOpeningsForTurn`)로 나눈다.
- **디자인 패턴**(아는 패턴을 따라 읽는 사람이 구조를 짐작할 수 있게):
  - **Strategy**: `TurnDecider`·`CleanupDecider` 자리에 `LlmTurnDecider`·`LlmCleanupDecider`가 들어간다. `runTurn`·`runCleanup`은 그대로다.
  - **Adapter**:
    - `ToolBox`는 OpenAI를 모른다. `toFunctionTools(toolBox)`가 도구 정의로 바꾼다.
    - `ChatClient` 포트가 SDK를 감싼다.
  - **Builder / 두 단계 조립**:
    - `assembleTurnInput`은 무엇을 보여 줄지(선택 규칙)만 정해 구조체를 낸다.
    - `renderTurnInput`은 그 구조체를 어떻게 쓸지(문서 형식)만 정한다.
    - 선택 규칙(꼬리·생략·`x` 빼기)과 형식을 따로 고칠 수 있다.
  - **Repository**:
    - SQL은 `db/repositories/` 안에만 둔다.
    - 새 저장소는 `llm-calls.ts`와 `plans.ts`(오늘 계획 읽기)다.
    - 입력 조립에 필요한 조회를 기존 저장소에 더한다.
  - **Composition Root**: `boot`가 `ChatClient`를 받아 실제 결정자를 조립한다. 계획 핸들러만 아직 주입받는다.
- 테스트도 같은 기준이다.
  - 테스트 이름은 정본 번호와 상황을 쓴다.
  - 본문은 주어진 상황 → 행동 → 기대 순으로 읽힌다.

### 정본 이름 → 코드 이름

| 정본 | 코드 | 하는 일 |
|---|---|---|
| `ctx = assemble(kind, x, day)` | `assembleTurnInput(ctx, task, planDate)` → `TurnInput` | 무엇을 보여 줄지 고른다 |
| (형식) | `renderTurnInput(input)` → system·user 메시지 | 문서 한 장으로 쓴다 |
| `upto` | `TurnInput.lastShownUserMessageId` | 입력에 넣은 user 메시지의 최대 id |
| `io_from` | `lastMessageIdBeforeIo` | 이후 id가 io 중 도착이다 |
| `out = await llm(ctx)` | `LlmConversation.ask(parseOutput)` | 도구 라운드 → 강제 호출 → 읽기 → 1회 재시도 |
| 되묻기 `llm(ctx + out + 피드백)` | `LlmConversation.askAgain(feedback, parseOutput)` | 같은 대화를 잇는다 |
| `judge` | `describeReplyProblem(completion)` | `llm_calls.error`에 남길 실패 사유 |
| `gone` | `deleteMessagesArrivedDuringIo(...)` → 지운 id | 커밋 tx가 `busy`로 표시 |
| typing 시작·해제 | `keepTypingDuring(ctx, work)` | io 동안 4초마다 표시, 끝나면 멈춘다 |

## 설계 결정

### 입력 배치: 문서 한 장 (사용자 선택, 시나리오 참고)

- **system**: `persona.md` + `turn-rules.md`. 정리는 `cleanup-rules.md`만 쓰고 persona는 넣지 않는다.
  - 바뀌지 않는 부분이라 앞에 두면 캐시 prefix가 된다.
- **user 메시지 하나**: 제목 붙은 절이고, 순서는 캐시를 기준으로 정한다.
  - 같은 흐름의 다음 턴에서도 앞부분이 글자 그대로 같아야 prefix 캐시가 산다.
  - 그래서 흐름 안에서 바뀌지 않는 절을 먼저 둔다: 방침, 기억, 오늘 계획, 직전 흐름.
  - 그 뒤에 덧붙기만 하는 흐름 대화를 둔다.
  - 턴 도구로 바뀌는 절(활성 목표, 오늘 종료된 목표, 개시 예약)과 매 턴 바뀌는 절(흐름 밖, 이벤트)은 맨 뒤에 둔다.
  - 모델이 읽는 순서는 이해 쪽에 조금 불리하다. 절 제목이 무엇의 "지금 상태"인지 말하게 해서 보완한다.
  - 예시는 시나리오 F5 20:41의 `Turn(continue)`다. 계획 예약 R4가 20:30에 연 AI 개시 흐름(`opener='ai'`)의 셋째 턴이다: 20:30 개시 → 20:34 답장 → 20:41 이어가기.
  ```
  ## 방침
  - sample: <description>
  ## 기억
  <state 전문>                              (비었으면 "state: (비어 있음)")
  칸: 가이드 원고, 조사 데이터, 도구로서의 사용자   (없으면 "칸: (없음)")
  ## 오늘 계획
  <본문>                                   (없으면 "(계획 전)")
  ## 직전 흐름
  15:27 종료                                (꼬리가 없으면 제목 줄은 남기고 그 아래 한 줄만 "(없음)")
  [15:27] 사용자: 1. 망원시장 빵은 오전에 동난다
          2. 오후에 가면 소금빵은 없다          (여러 줄은 들여쓰기)
  [15:27] 나: 1번. 다음에 핑계 댈 거면 ...
  ## 흐름 대화
  [요약] 오후에 빵집 섹션 초안을 냈다. ...     (압축된 흐름만. 압축 단계, compact.md)
  [20:30] 나: 빵집 섹션 마무리. ...
  [20:34] 사용자: 그냥 지금 것도 충분하지 않아? ...
  [20:34] 나: 숫자는 너 없이도 표로 쓴다. ...
  ## 지금 활성 목표
  - #2 빵집 섹션 완성 (sample, 마감 2026-10-31 22:00, 개시 예약 #6, #7)
    완료 조건: 숫자는 본 것만, 소개는 사용자 문장
    진행 메모: 숫자 반영본 있음. 남은 것: 소개 문장, 근거 확인   (비었으면 "(없음)")
    방침 사본:
      <job_snapshot 본문, 줄마다 6칸 들여쓰기>
  ## 오늘 종료된 목표
  - #1 모래 영업시간 [done] 사장 통화: 10–21시 ...
  - #3 첫 문장 3버전 [failed] 16:30까지 안 씀
  - #4 카페 사진 [dropped] 비 와서 내일로
  ## 지금 개시 예약
  - #6 2026-10-31 21:00 마무리 확인 [목표 2] (turn)
  - #7 2026-10-31 21:30 후속 확인 [목표 2] (harness) 밀림
  - #8 2026-10-31 22:00 하루 정리 (plan)
  ## 흐름 밖 메시지
  (없음)                                    (판정 턴이면 "(이전 흐름 밖 메시지 5개 생략)" + 줄들, 무시한 것은 "(무시됨)")
  ## 이벤트
  계기: 이어가기
  개시 의도: 빵집 섹션 마무리
  예정: (없음)
  지금: 2026-10-31 20:41
  오늘의 끝: 2026-11-01 00:00
  ```
- **이벤트 절**은 늘 다섯 줄이고 이 순서다. 해당 없는 값은 `(없음)`이다.
  - `계기:` 턴 종류(§9.4)마다 하나다.

    | 턴 | 계기 줄 |
    |---|---|
    | `open` | `AI 개시(개시 예약 #4)` |
    | `user` | `사용자 메시지(흐름 없음)` |
    | `reply` | `사용자 답장` |
    | `continue` | `이어가기` |

    판정 턴과 답장 턴은 둘 다 사용자 말에서 생기지만, 흐름이 있는지가 다르다. 그래서 계기 이름부터 다르다. 각본 모델도 이 줄로 트리거를 읽는다.
  - `개시 의도:` 이 흐름을 연 개시 예약의 `intent`다. AI 개시 턴은 그 예약 `x`의 intent이고, AI 개시 흐름의 이후 턴은 `opened_intent`다(23a).
    - 사용자가 연 흐름(판정 턴과 그 흐름의 모든 이후 턴)은 `opened_intent`가 NULL이라 `(없음)`이다. 빠뜨린 게 아니라 정해진 값이다.
  - `예정:` AI 개시 턴에서만 `2026-10-31 20:30 (11분 늦음)`이다. 그 밖의 턴은 `(없음)`이다(30a).
  - AI 개시 턴의 `x`(`#4`)는 `## 지금 개시 예약`에 나오지 않는다(§5.1, 58a).
  - AI 개시 턴의 이벤트 절 예:
    ```
    ## 이벤트
    계기: AI 개시(개시 예약 #4)
    개시 의도: 빵집 섹션 마무리
    예정: 2026-10-31 20:30 (11분 늦음)
    지금: 2026-10-31 20:41
    오늘의 끝: 2026-11-01 00:00
    ```
    - 늦은 정도는 `지금 - at`을 분 단위로 버린 값이다.
    - 1분 미만이면 `(제시간)`, 60분 미만이면 `N분 늦음`, 그 이상이면 `H시간 M분 늦음`이다. 분이 0이면 `H시간 늦음`으로 쓴다.
    - 정본 예시 "09:00 예정, 5시간 늦음"은 `예정: … 09:00 (5시간 늦음)`이 된다.
  - 판정 턴(`Turn(user)`, 흐름 없음) 예시. 다른 절은 위와 같은 형식이다.
    ```
    ## 흐름 대화
    (없음)
    ## 흐름 밖 메시지
    (이전 흐름 밖 메시지 5개 생략)
    [15:10] 사용자: 심심하다 (무시됨)
    [15:20] 사용자: ㅋㅋㅋㅋ 고양이가 식빵 자세로 자는 거 봤음?
    ## 이벤트
    계기: 사용자 메시지(흐름 없음)
    개시 의도: (없음)
    예정: (없음)
    지금: 2026-10-31 15:20
    오늘의 끝: 2026-11-01 00:00
    ```
    - 흐름 밖 메시지는 판정 턴과 AI 개시 턴(13)에 나온다. 흐름을 여는 커밋이 다 옮기므로 흐름 안 턴(이어가기·답장)에서는 늘 `(없음)`이다.
- **절 내용 규칙**:
  - 절은 늘 같은 순서·같은 제목으로 모두 나온다. 비면 절을 빼지 않고 `(없음)`을 쓴다.
    - 목록 절(목표·예약·대화·흐름 밖)과 직전 흐름 꼬리 모두 이 규칙을 따른다. 꼬리가 없는 경우는 첫 흐름, `prev_flow_tail_max_age_sec`을 넘긴 흐름(48b)이다.
    - 기억은 `state: (비어 있음)`, `칸: (없음)`이다.
    - 슬롯이 흔들리면 뒤의 prefix도 깨진다.
    - AI 개시 턴에서 `x`가 유일한 예약이면 `## 지금 개시 예약`이 `(없음)`이다. 슬롯이 늘 같은 자리에 있어야 모델이 "없음"과 "안 보여 줌"을 구분한다.
  - 방침 줄은 `- <id>: <description>`이다. 순서는 파일명 사전순이다(`loadPrompts`가 이미 정렬한다). 재시작해도 prefix가 같다.
  - 기억의 칸 제목은 `칸: 제목1, 제목2`이고, `created_at` 순이다(§8.7, `listSections`가 이미 그렇게 읽는다).
  - 활성 목표 줄은 `#id 제목 (job_id, 마감 …, 개시 예약 #…)`이다. 마감·예약이 없으면 그 항목을 뺀다. 그 아래에 들여쓴 `완료 조건:`, `진행 메모:`, `방침 사본:`(본문을 한 단계 더 들여쓴다)이 온다.
    - 방침 사본은 목표마다 수백 자라 `goal_max_active`개면 수천 자다. 정본이 평가 기준으로 넣으라고 한 것이라 줄이지 않는다.
    - 이 절은 흐름 대화 뒤에 있어서 `goal_create`가 일어나도 흐름 대화까지의 prefix는 산다.
  - 목표에 걸린 개시 예약은 전부 나열한다(`개시 예약 #6, #7`). 시나리오 122처럼 한 목표에 예약이 여럿 걸린다.
    - AI 개시 턴의 `x`는 여기서도 뺀다. 도구 검증이 `x`를 이미 지운 것으로 보므로(§9.5, L5) 입력도 같은 상태를 보여 준다.
  - 개시 예약 줄은 `#id at intent [목표 ids] (source)`이고, `fired`면 `밀림`이 붙는다. 순서는 `at`, 같으면 `id`다(§5.1).
    - `source`는 `turn`·`plan`·`harness` 셋 다 그대로 쓴다.
    - `harness` 예약의 intent는 저장된 "후속 확인"이 나온다.
    - 목표가 없으면 `[목표 …]`를 뺀다.
  - 오늘 계획은 `plans`에서 그 턴의 계획일 행의 본문이다. 행이 없으면 `(계획 전)`이다(48d).
    - 계획은 아직 가짜 핸들러다. 그래서 `FakePlan.finishPlan({ body })`가 `plans` 행도 쓰게 한다(가짜가 결과를 직접 쓰는 기존 방식 그대로).
  - 직전 흐름 꼬리(§5.1):
    - 가장 최근에 닫힌 흐름을 고른다. 그 종료 시각이 `기준 시각 - prev_flow_tail_max_age_sec`보다 뒤면 넣는다.
    - 넣는 것은 그 흐름의 마지막 `prev_flow_tail_messages`개 메시지다. `void_reason`이 있는 메시지는 뺀다.
    - 기준 시각은 이 흐름의 첫 메시지 시각이다. 흐름이 없으면 흐름 밖 메시지 중 가장 이른 것, 그것도 없으면 지금이다.
    - 종료가 기준 시각보다 뒤여도 넣는다(48g).
  - 오늘 종료된 목표는 그 턴의 계획일 목표 중 `active`가 아닌 것이다. `[결과] 사유` 형식이다.
    - 결과는 `done`·`failed`·`dropped`가 나온다.
    - `expired`는 날 넘김이 지난 계획일 목표에만 붙이므로, 오늘 계획일의 목표에는 생길 수 없다.
    - `expired`와 `failed`를 가르는 일은 계획 입력(75g, 계획 단계)이 맡는다.
  - 흐름 대화의 assistant 줄은 보낸 메시지 본문이다. 출력 JSON(`next`, `continue_at`)은 다시 보여 주지 않는다.
    - 커밋이 출력의 `messages`를 한 줄에 한 행씩 저장하므로, DB의 assistant 메시지가 곧 사용자가 받은 말이다.
    - JSON을 다시 보여 주면 모델이 자기 `next`를 따라 하려 하고, 대화와 출력 형식을 헷갈릴 수 있다.
    - "assistant는 JSON 원문"은 옛 판(`docs/archive/harness-design-v3.md` 현재 흐름 대화 표)의 규정이다. 정본 1.0에는 없다.
      - 1.0의 `messages`(§8.5)는 메시지 하나가 한 행이고, §9.4 커밋도 "assistant 메시지 삽입"이다. 그래서 정본과 이 결정은 이미 맞다.
      - 다만 1.0 §5.1 입력 행의 "흐름 대화"가 형식을 말하지 않아 v3를 읽은 사람이 헷갈릴 수 있다. 문서 커밋에서 §5.1에 "assistant 줄은 보낸 메시지 본문(출력 JSON 아님)" 한 줄을 더한다.
- 시나리오(`harness-scenario-agent-owner-shortcuts.md`)에서 끌어온 요구와 그 자리:

  | 장면 | 필요한 것 | 입력의 자리 |
  |---|---|---|
  | C1 가격·문체 대조 | 기억 칸 제목. 본문은 `memory_read`로 읽는다 | `## 기억` |
  | C2 수정된 메시지 | 저장된 원문 그대로, 메시지별 시각 | `## 흐름 대화`의 `[HH:mm] 사용자:` 줄 |
  | C3 핑계 뒤 잡담 | 직전 흐름의 마지막 몇 줄과 종료 시각 | `## 직전 흐름 (… 종료)` |
  | F4 16:00 예약 | 목표에 걸린 예약 id, 오늘 닫힌 목표와 사유 | `## 지금 활성 목표`, `## 오늘 종료된 목표` |
  | F5 낮의 상태를 저녁에 이음 | 진행 메모, 개시 의도, 늦어진 정도 | `## 지금 활성 목표`, `## 이벤트` |

- **시각 표기**:
  - 예약·마감·이벤트 시각은 도구 인자와 같은 로컬 `YYYY-MM-DD HH:mm`이다. 모델이 그대로 베껴 도구에 넣을 수 있다.
  - 대화 줄과 직전 흐름 종료 시각은 `HH:mm`이다. 지금과 로컬 날짜가 다르면 `MM-dd HH:mm`로 쓴다(전날 밤 꼬리의 `10-30 23:00 종료`).
- **빼는 것**: `void_reason`이 있는 메시지(`busy`, `trimmed`, `undelivered`)는 턴·정리 입력에 넣지 않는다. `ignored`는 넣고 "(무시됨)"을 붙인다.

### 정리 입력

- **system**: `cleanup-rules.md`. persona는 넣지 않는다.
- **user 문서**: 턴과 같은 규칙(제목 고정, 비면 `(없음)`, 시각 표기)을 따른다.
  ```
  ## 기억
  <state 전문>
  칸: 가이드 원고, 조사 데이터, 도구로서의 사용자
  ## 흐름
  개시: AI(개시 의도: 빵집 섹션 마무리) / 사용자
  시작: 2026-10-31 20:30 / 종료: 2026-10-31 21:06 (agent | blackout | stale | failed)
  ## 목표 (계획일 2026-10-31)
  - #2 빵집 섹션 완성 (sample) [done] 숫자는 본 것만, ... — 이 흐름에서 다룸
    완료 조건: … / 진행 메모: …
  - #1 모래 영업시간 (sample) [done] 사장 통화: ...
  - #5 카페 섹션 (sample) [active]
  ## 대화
  [20:12] 사용자: 오늘 저녁 뭐 먹지 (무시됨)     (흐름을 열 때 옮겨진 메시지. id 순)
                                               (원문이 cleanup_raw_max_chars를 넘을 때만 맨 앞에 [요약] 줄과 비압축 구간. compact.md)
  [20:30] 나: 빵집 섹션 마무리. ...
  [20:34] 사용자: ...
  ## 지금
  2026-10-31 21:07
  ```
- 목표는 흐름 계획일의 목표 전체에 `flow_goals`의 목표를 더한 것이다. `flow_goals`에 있으면 `이 흐름에서 다룸`을 붙인다(90a, 90k).
  - 방침 사본은 넣지 않는다. 정본 §5.3이 제목·완료 조건·`job_id`·상태·진행 메모·종료 사유만 든다.
- 정리는 흐름당 한 번이라 캐시 순서를 따지지 않는다. 읽는 순서대로 둔다.

### 출력 스키마

- 턴 출력 JSON:
  ```json
  { "messages": ["..."], "next": "continue" | "end", "continue_at": "YYYY-MM-DD HH:mm" }
  ```
  - `continue_at`은 `continue`일 때만 쓰고, 빠져도 된다. 빠지거나 과거면 `fitContinueTime`이 메운다(46).
  - 형식이 틀린 값(`"아침"`)은 파싱 실패다.
- 트리거별 차이는 스키마 쪽에서 처리한다. 이어가기 턴의 "메시지 0개 + `continue`"는 스키마 위반이다.
  - 2단계에서 `runTurn`의 `checkedOutput`이 하던 일을 스키마로 옮긴다.
  - 그래서 파싱 재시도 1회를 탄다(48h).
- 정리 출력: JSON 객체면 받는다. 결과는 도구 효과가 전부다.
- 파서는 `(text) => { ok, value } | { ok: false, error }`이다. 실패 사유는 재시도 피드백과 `llm_calls.error`(`parse: ...`)에 그대로 쓴다.

### 실행기 (`LlmConversation`)

```
ask(parse):
  for round = 0..:
    isForced = round >= maxToolRounds
    reply = send(isForced)                       # API 오류면 LlmCallError(api)
    if reply.tool_calls and not isForced:
      assistant(tool_calls) + 각 호출의 tool 결과(JSON 문자열)를 대화에 잇는다; continue
    parsed = parse(reply.content)
    if parsed.ok: 대화에 assistant(content) 잇고 return parsed.value
    대화에 잘못된 답 + "출력이 형식에 맞지 않는다: <사유>"를 잇고 send(forced) 한 번 더
    둘째도 실패면 LlmCallError(output)
askAgain(feedback, parse): 대화에 user(feedback)를 잇고 ask(parse)   # 라운드 상한은 새로 센다
```

- **도구 실행**:
  - 인자가 JSON이 아니거나, 함수 도구가 아니거나, 없는 이름이면 거부 결과를 문자열로 돌려준다. 예외로 끊지 않는다.
  - 결과는 `ToolResult`를 JSON으로 바꾼 것이다.
- **요청 기록(`send`)**:
  - `daily_calls`를 1 늘린다. 날짜가 바뀌었으면 먼저 0으로 되돌린다.
  - `llm_calls`에 한 행을 쓴다: `kind`, `flow_id`, request·response JSON, 토큰, `latency_ms`, `success`, `error`.
    - 흐름을 여는 턴은 아직 흐름이 없어 `flow_id`가 NULL이다.
  - 각 기록은 자동 커밋이다. io 동안 tx를 열지 않는 2단계 원칙을 그대로 따른다.
- **요청 형태**:
  - `response_format: json_object`를 붙인다.
  - `reasoning_effort`는 설정에 있을 때만 넣는다.
  - 강제 호출에도 `tools`를 유지한다(`docs/notes/openai-adapter.md`).

### 턴과 텔레그램

`runTurn`의 pre/io 부분만 바뀐다. 커밋(`commitTurn`)은 지운 id 목록 하나만 더 받는다.

```
pre:  planDate; input = assembleTurnInput(...); lastMessageIdBeforeIo = MAX(messages.id)
      TurnRequest에 input을 더해 결정자에 넘긴다. upto는 input.lastShownUserMessageId
io:   keepTypingDuring(흐름 안 턴만, decide + 되묻기)
      if 말하는 출력 and not (AI 개시 and 블랙아웃):
        busyMessageIds = deleteMessagesArrivedDuringIo(lastMessageIdBeforeIo)   # 실패한 것은 남긴다
commit: 2단계와 같고, 말한 턴이면 busyMessageIds → void_reason='busy'
```

- 되묻기 피드백(`LlmTurnDecider`가 쓴다)은 §9.4 문구를 따른다:
  ```
  다음 목표에 다음 확인이 없다:
  - #2 빵집 섹션 완성
  open_reserve로 시각을 잡거나, open_update로 기존 예약에 붙이거나, goal_close하라.
  오늘의 끝까지 남은 시간: 1시간 54분
  ```
  - 목표 줄은 `- #id 제목`이다. 각본 모델이 이 줄에서 `goalsWithoutNextCheck`를 읽는다.
  - 그날 남은 시간이 없는 목표는 2단계에서 이미 목록에서 뺀다. 남은 시간 줄은 AI가 예약 대신 `goal_close`를 고를 근거다.
- 입력 중 표시는 4초마다 다시 보낸다. 텔레그램 표시는 5초 뒤 사라지고 "해제" API가 없다. 타이머는 `clock.setTimer`를 쓴다.

### 가짜 경계: 각본 모델

`ScriptedLlm`은 `ChatClient`를 구현한다. 계획 핸들러는 그대로 둔다. 각본 문법은 거의 그대로이고, 도구 호출만 `await`가 붙는다.

```ts
new ScriptedLlm()
  .onTurn(async (turn) => {
    const goalId = await turn.createGoal({ title: "산책" });       // tool_calls completion → 결과 대기
    await turn.reserveOpening({ at: "15:00", goalIds: [goalId] });
    return turn.say("나가서 걸어", { continueAfter: { minutes: 30 } }); // 최종 JSON completion
  })
```

- **요청 분류**: 요청을 보고 정한다. 단일 루프라 진행 중인 대화는 하나뿐이다.
  - assistant 메시지가 없으면 새 대화다. `tools`에 `goal_create`가 있으면 턴, `state_write`가 있으면 정리다.
  - 마지막이 `tool` 메시지면 각본의 대기 중인 `use`를 그 결과로 깨운다.
  - 최종 답 뒤에 user 피드백이 오면 되묻기다. 피드백의 목표 줄에서 `goalsWithoutNextCheck`를 읽는다.
  - 잘못된 답 뒤의 강제 호출은 파싱 재시도다.
  - 각본이 도구를 기다리는 중에 강제 호출이 오면, 그 `use`는 `{ ok: false, reason: "도구를 쓸 수 없는 호출" }`로 풀리고 각본은 이어서 최종 출력을 낸다.
- **트리거**: 이벤트 블록의 `계기:` 줄에서 읽는다. 실제 모델이 읽는 것과 같은 자리라, 계기가 입력에서 빠지면 테스트가 깨진다(의도).
- **출력 도우미**:
  - `say`, `end`, `silent`, `silentEnd`는 그대로다.
  - `malformed({ onRetry? })`는 형식이 틀린 답을 낸다. `onRetry`가 없으면 재시도에도 틀린다.
  - `cleanup.fail()`·`turn.apiError()`는 API 오류를 던진다.
- **관찰**:
  - `app.llm.requests`(받은 요청 전부)
  - `app.llm.lastInput("turn")`: 렌더된 user 문서
  - `inputSection(doc, "흐름 대화")`: 절 하나의 줄
  - `llmTasks`는 각본 모델이 대화 시작마다 기록한다. 형식은 그대로다.
- **반복 상한**: 상한(300)을 넘으면 응답을 영영 보내지 않는다. 그 사실을 `shutDown`이 오류로 보고한다.
  - 실행기는 `create`의 예외를 API 실패로 받아 버리고 루프가 같은 작업을 다시 고르므로, 예외로는 반복이 멈추지 않는다.
- **테스트 설정 기본값**: 각본은 라운드마다 도구 하나를 부르므로 `max_tool_rounds`·`max_cleanup_tool_rounds`를 넉넉히(20) 둔다. 상한을 보는 테스트만 낮춘다.

### 프롬프트와의 경계

- 하네스는 프롬프트 본문을 쓰지 않는다. 방침과 프롬프트는 사용자가 쓴다.
- `turn-rules.md`·`cleanup-rules.md`를 쓰는 데 필요한 계약은 `docs/plans/llm-executor.md`에 남긴다: 입력 절과 형식, 출력 JSON, 도구 이름·인자, 되묻기·재시도 피드백 문구.
- 하네스가 모델에게 직접 하는 말은 둘뿐이다. 둘 다 계약 문서에 그대로 싣는다.
  - 파싱 재시도 피드백
  - 되묻기 피드백

## 테스트 전략 (이전 계획에서 이어짐)

**기본은 e2e.** spec 테스트는 내부 함수(`assembleTurnInput`, `LlmConversation`)를 직접 부르지 않는다. 앱을 실제로 부팅하고, 바깥 경계로만 넣고 본다.
- 가짜는 시계, 텔레그램, `ChatClient`(각본 모델), 계획 핸들러뿐이다.
- **입력은 모델이 받은 요청으로 본다.**
  - 테스트는 렌더된 문서의 절을 꺼내 줄 단위로 비교한다(`inputSection`).
  - 문서 전체 스냅숏은 쓰지 않는다. 형식을 조금 바꿀 때마다 무관한 테스트가 깨지기 때문이다.
  - 대신 각 테스트는 자기가 보는 절만 정확히 비교한다.
- **실행기는 요청 순서와 `llm_calls`로 본다.**
  - 라운드 수, 강제 호출의 `tool_choice`와 `tools` 유지, 재시도 요청의 피드백, 기록 행을 본다.
- **단위 테스트는 경계값이 많은 순수 함수에만** 둔다. 출력 파서가 여기에 해당한다.
  - 빠진 `next`, `end`와 `continue_at`이 함께 온 경우, 틀린 시각 형식, 문자열이 아닌 메시지
  - 트리거별 "말 없이 이어가기"
  - JSON이 아닌 텍스트, 코드 펜스로 감싼 JSON

## 프롬프트 작성용 계약

`turn-rules.md`·`cleanup-rules.md`를 쓸 때 기준이다. 입력 절과 형식은 위 "입력 배치"와 "정리 입력"이 정본이고, 여기에는 나머지를 모은다.

**턴 출력** (`response_format: json_object`)

```json
{ "messages": ["보낼 말", "..."], "next": "continue", "continue_at": "2026-10-30 15:00" }
{ "messages": [], "next": "end" }
```

- `messages`의 항목 하나가 텔레그램 메시지 하나다. 빈 문자열은 안 된다.
- `continue_at`은 `next`가 `continue`일 때만 쓴다. 빠지거나 과거면 하네스가 `continue_default_sec` 뒤로 메운다.
- 이어가기 턴(`계기: 이어가기`)에서 "메시지 0개 + `continue`"는 형식 위반이다.

**정리 출력**: JSON 객체 하나면 된다(예: `{}`). 결과는 도구 효과가 전부다.

**시각**: 도구 인자와 `continue_at`은 설정 시간대의 로컬 `YYYY-MM-DD HH:mm`이다. 초를 붙인 `HH:mm:ss`도 받는다.

**턴 도구**

| 도구 | 인자 | 결과(`ok: true`일 때) |
|---|---|---|
| `job_read` | `job_id` | `prompt`(방침 본문) |
| `memory_read` | `title` | `content` |
| `goal_create` | `job_id`, `title`, `done_criteria`, `due_at?` | `goal_id` |
| `goal_update` | `goal_id`, `progress?`, `due_at?` | |
| `goal_close` | `goal_id`, `result`(`done`·`failed`·`dropped`), `reason` | |
| `open_reserve` | `at`, `intent`, `goal_ids?` | `reservation_id`, 보정된 `at` |
| `open_update` | `reservation_id`, `at?`, `intent?`, `goal_ids?` | |
| `open_cancel` | `reservation_id` | |

**정리 도구**: `memory_read`(`title`), `state_write`(`content`), `memory_write`(`title`, `content`), `memory_delete`(`title`).

- 도구 결과는 모두 JSON 문자열이다: `{ "ok": true, ... }` 또는 `{ "ok": false, "reason": "..." }`.
- 거부 이유에는 상한 값, 지금 개수·길이, 그날 끝 시각이 들어 있다. 모델은 그것을 보고 고쳐 다시 부른다.

**하네스가 모델에게 직접 하는 말**

- 파싱 재시도(강제 호출, 한 번):
  ```
  출력이 형식에 맞지 않는다: <사유>
  형식에 맞는 JSON 객체 하나로 다시 답하라.
  ```
- 되묻기(흐름이 없어지는 출력에서 다음 확인이 없는 목표가 남을 때, 한 번):
  ```
  다음 목표에 다음 확인이 없다:
  - #2 빵집 섹션 완성
  open_reserve로 시각을 잡거나, open_update로 기존 예약에 붙이거나, goal_close하라.
  오늘의 끝까지 남은 시간: 1시간 54분
  ```

## 구현 결과

계획한 커밋 단위대로 들어갔다(68e9d85 → 이 문서). 달라진 점과 알아둘 점은 아래와 같다.

- **주입.** `boot`는 `createDeciders` 대신 `chat: ChatClient`와 `runPlan(ctx, task)`을 받는다. 턴·정리 결정자는 `boot`가 만든다.
- **각본 가짜.**
  - 파일명이 `test/fakes/llm-tasks.ts`에서 `test/fakes/scripted-llm.ts`로 바뀌었다.
  - 파싱 재시도는 재시도 피드백 문구로 알아본다. 형식은 맞지만 하네스가 거부한 답(48h)도 재시도로 받는다.
  - 각본이 낸 이어가기 시각은 초가 0이 아니면 초까지 쓴다. 디바운스 20초 뒤의 시각을 그대로 재는 기존 기대를 지키려는 것이다. 그래서 `continue_at`과 도구 시각이 초를 받게 했다(위 계약).
- **기존 e2e.** 기대값은 바뀌지 않았다. 각본에 `await`가 붙었고, 아래만 준비가 바뀌었다.
  - 62e: 되묻기 실패를 예외 대신 `malformed()`로 만든다.
  - 25: 되묻기 목표를 피드백 문구에서 읽는다.
  - 13(→ "13, 31"), 21, 67(→ "12, 67"): 말하는 턴의 io 중에 메시지가 온다. 이 테스트들이 보는 것은 지우기에 실패한 경로라서, 지우기 실패를 주입한다.
- **흐름 대화의 순서.** 메시지는 id 순이다.
  - 그래서 io 중에 와서 지우지 못한 메시지는, 그때 진행 중이던 턴의 답보다 앞에 나온다(44).
  - 모델이 "이미 답한 말"로 읽을 수 있다. 정본대로 두고 턴 규칙에서 다룬다: 사용자 말 바로 뒤의 내 답이 그 말과 맞지 않으면 아직 답하지 않은 말로 본다([`prompts.md`](prompts.md)).
- **턴 실패**는 아직 "경고 후 버림"이다. 같은 실패가 반복되면 같은 작업을 바로 다시 고른다(턴 실패 단계에서 막는다).
  - 4단계에서 처리했다: 시도 선기록, `failTurn`, 트리거 포기, 운영자 알림. [`turn-failure.md`](turn-failure.md).
- **계획**은 아직 가짜 핸들러다. `FakePlan`이 `plans` 행을 쓴다.
  - 6단계에서 실행기로 옮겼다. [`plan.md`](plan.md).
