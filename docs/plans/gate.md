# 5단계 구현 계획: 게이트

## Context

4단계까지 LLM 호출은 예산을 확인하지 않는다.
- `daily_calls`는 세기만 하고(`countLlmRequest`), 상한에 닿아도 아무것도 막지 않는다.
- `deepseek` 잔액도 확인하지 않는다.
- 보류 해제(`checkHoldRecovery`)와 보류 중 작업 고르기는 이미 있지만, `daily_limit`·`balance` 보류에 들어가는 경로가 없다. 그래서 11.14 테스트는 보류를 DB에 직접 심는다(`plant`).
- `blocked` 진입(403)은 운영자 알림을 하지 않는다. 4단계에서 미룬 "blocked 중 알림은 로그만" 테스트도 이 경로가 있어야 쓸 수 있다.

이번 단계는 정본 §6.3의 게이트 `gate()`와 보류 진입(알림 포함), 잔액 확인을 넣는다. 실물 API를 붙이기 전의 마지막 비용 안전장치다.

## 범위

**포함**
- **게이트:** LLM 작업이 상태를 바꾸기 전에 일일 상한과 잔액을 확인하고, 모자라면 보류에 들어간 뒤 아무것도 바꾸지 않고 끝난다.
  - 턴: 시도 선기록보다 앞(§9.4)
  - 정리: 포기 검사 뒤, 시도 선기록 앞(§9.6)
  - 계획: 아직 가짜라 `boot`에서 계획 작업을 넘기기 전에 건다. 계획 단계에서 `runPlan` 안으로 옮긴다.
- **보류 진입 `enterHold`:** `hold_reason`·`hold_since`·`hold_until`을 기록하고 운영자에게 알린다. 403의 `blocked` 진입도 이것을 쓴다(보류가 `blocked`라 알림은 로그만 남는다).
- **잔액 해제:** `balance` 보류가 `hold_until`에 닿으면 잔액을 다시 확인한다. 회복했으면 풀고 `resume()`, 아니면 `hold_until = now + balance_retry_sec`.
- **잔액 포트 `BalanceSource`:** 테스트는 가짜, 실물(DeepSeek `/user/balance`)은 어댑터 단계.
- **바뀌는 테스트:** 보류를 심던 테스트를 실제 경로로 바꾼다(아래 표).

**제외**
- 압축 단계: 압축의 게이트는 압축과 함께 넣는다.
- 계획 단계: 계획의 실제 LLM 호출과 `daily_calls` 집계. 지금 가짜 계획은 요청을 세지 않는다.
- 어댑터 단계: DeepSeek 잔액 API 호출과 "통화 단위가 다르면 경고"(응답의 통화를 아는 곳이 어댑터다).

## 코드 작성 원칙 (이전 계획에서 이어짐)

- **이름:** 이름만 보고 하는 일을 알 수 있게 한다. 함수는 동사구, 불리언은 `is`/`has`, 시각은 `...At`.
- **주석:** 이름과 구조로 설명할 수 없는 이유에만 단다. 이번 단계의 예:
  - 왜 상태를 바꾸기 전에 확인하는가(반쯤 바뀐 상태를 남기지 않는다)
  - 왜 일일 상한을 작업 단위로 판정하는가
  - 왜 잔액 확인이 실패하면 통과시키는가
- **함수 하나는 한 단계의 추상만 다룬다.** 각 작업의 첫 줄이 `if (await holdIfOutOfBudget(ctx)) return;`로 읽히게 한다.
- **패턴:** SQL은 저장소 안에만. 보류 사유별 동작은 `hold.ts`의 `switch` 하나에 모은다(이미 있는 `isHoldRecovered`와 같은 모양).
- **테스트:** 이름은 정본 번호와 상황, 본문은 주어진 상황 → 행동 → 기대.

### 정본 이름 → 코드 이름

| 정본 | 코드 | 하는 일 |
|---|---|---|
| `gate()` | `holdIfOutOfBudget(ctx): Promise<boolean>` | 예산이 모자라면 보류에 들어가고 `true` |
| 보류 진입 | `enterHold(ctx, reason, until)` | 기록하고 운영자에게 알린다 |
| `try_release()` | `checkHoldRecovery(ctx)` (있음) | `balance`면 잔액을 다시 확인하도록 고친다 |
| 오늘 요청 수 | `countTodaysLlmRequests(ctx, state)` | `daily_calls_date`가 오늘이 아니면 0 |
| 잔액 조회 | `ctx.balance.fetchBalance()` | 포트 |

## 설계 결정

### 게이트

```
holdIfOutOfBudget():
  state = harnessState.get()
  if countTodaysLlmRequests(state) >= daily_call_limit:
    enterHold('daily_limit', until = 다음 로컬 자정); return true
  if provider == 'deepseek':
    balance = fetchBalance()                 # 실패하면 경고 로그 후 통과
    if balance < balance_threshold:
      enterHold('balance', until = now + balance_retry_sec); return true
  return false
```

- **일일 상한을 먼저 본다.** 상한에 닿았으면 잔액 API를 부르지 않는다.
- **오늘 요청 수는 지연 리셋을 따른다.** `daily_calls_date`가 오늘이 아니면 0으로 본다. 쓰기는 하지 않는다. 리셋 쓰기는 지금처럼 요청 직전의 `countLlmRequest`가 한다(112).
- **작업 단위 판정:** 게이트는 작업 시작에 한 번만 본다. 그 작업의 도구 라운드·파싱 재시도·되묻기가 상한을 넘는 것은 허용한다(§6.3).
- **잔액 확인이 실패하면(네트워크 등) 통과시킨다.** 정본이 정하지 않았다.
  - 막으면 잔액 API만 죽은 경우에도 대화가 멈춘다.
  - 통과시키면 LLM API도 같이 죽은 경우 턴 실패의 백오프가 막는다. 비용이 새지 않는다.
- **보류 중에는 게이트까지 오지 않는다.** `pickNextTask`가 보류 중이면 LLM 작업을 고르지 않는다(이미 있음).

### 보류 진입

```
enterHold(reason, until):
  harnessState.enterHold(reason, since = now, until)
  alertOperator(문구)          # blocked면 alertOperator가 로그만 남긴다
```

- 알림 문구:
  - `daily_limit`: "오늘 LLM 요청이 상한(500건)에 닿아 보류에 들어간다. 2026-10-31 00:00에 풀린다."
  - `balance`: "잔액(0.8)이 기준(1)보다 적어 보류에 들어간다. 2026-10-30 11:00에 다시 확인한다."
  - `blocked`: "사용자가 봇을 차단해 보류에 들어간다. 사용자가 다시 메시지를 보내면 풀린다."
- **보류 해제는 로그만 남긴다**(지금처럼). 정본에 해제 알림이 없고, 해제 뒤 밀린 대화가 바로 이어지므로 사용자가 안다.

### 잔액 해제

- `isHoldRecovered`가 `balance`에서 `false`를 돌려주던 것을, 잔액을 다시 조회해 `>= balance_threshold`인지 보도록 바꾼다. 그래서 `checkHoldRecovery`가 잔액 조회를 기다린다(이미 async).
- 조회가 실패하면 회복하지 않은 것으로 보고 `balance_retry_sec` 뒤에 다시 본다. 게이트와 반대인 이유: 여기서 풀면 회복을 모른 채 호출이 나간다.

### 잔액 포트

```ts
// ports.ts
export interface BalanceSource {
  /** 지금 잔액. 단위는 balance_threshold와 같다고 본다. */
  fetchBalance(): Promise<number>;
}
```

- `HarnessContext.balance`, `BootOptions.balance`.
- 테스트 가짜 `FakeBalance`: `amount`를 바꿀 수 있고, 조회 횟수(`fetchCount`)를 세며, 다음 조회를 실패시킬 수 있다.

### 저장소

새 쿼리는 없다. `enterHold`, `postponeHoldCheck`, `clearHold`가 이미 있다.

### 기존 테스트에서 바뀌는 것

모두 "게이트가 없어서 보류를 심는다"던 테스트다. 실제 경로로 보류에 들어가게 바꾸고, 무엇을 보는지는 그대로 둔다.

| 테스트 | 지금 | 바뀐 뒤 |
|---|---|---|
| 11.14 108, 109, 111, 111a, 111b | `holdForDailyLimitUntilMidnight`로 심음 | `daily_call_limit`을 낮게 두고 실제 턴으로 상한을 채운다. 보류는 그다음 LLM 작업의 게이트에서 들어간다. 시각이 달라지면 그 이유를 커밋 메시지에 적는다 |
| 11.03 20 | `daily_limit`을 심음 | 같은 방식의 실제 경로 |

## 테스트 전략 (이전 계획에서 이어짐)

- **기본은 e2e다.** 앱을 부팅하고, 낮은 `daily_call_limit`과 가짜 잔액으로 보류를 만든다.
- **관찰은 바깥에서 보이는 것 위주:**
  - LLM 작업이 언제 나갔는지(`llmTasks`)
  - 잔액을 몇 번 조회했는지(`balance.fetchCount`)
  - 알림 수와 문구(`telegram.alerts`, 로그)
  - 트리거가 그대로인지(예약 `fired`, 메시지 `pending`)
  - `harness_state`는 정본이 값으로 정한 것(`hold_*`, `failure_count`, `turn_retry_at`, `cleanup_attempts`)만 직접 본다.
- **단위 테스트는 추가하지 않는다.** 게이트는 상태 전이라 e2e가 맞다.

## 검증

- `pnpm check`(fmt, lint, typecheck, test)가 통과해야 한다.
- 기존 235개 테스트 가운데 위 표의 것 말고는 기대값이 바뀌지 않아야 한다. 테스트 설정의 `daily_call_limit`=500이라 다른 테스트는 게이트에 걸리지 않는다.
- 손으로 따라가 볼 예 (107 + 109):
  - `daily_call_limit`=1. 10:00 "안녕" → 10:00:20 판정 턴(요청 1건, `daily_calls`=1). 말 없이 무시.
  - 개시 예약 12:00 발화 → 게이트: 1 >= 1 → 보류 `daily_limit`, `hold_until`=10-31 00:00, 알림 1번. 예약 `fired`.
  - 다음 기한 = `hold_until`. 00:00 `checkHoldRecovery`: 날짜가 바뀜 → 해제 → `resume()`.
  - 00:00은 블랙아웃이라 날 넘김이 어제 예약을 지운다. 계획(10-31)이 돈다.

  - 게이트는 상태를 바꾸기 전, 턴은 선기록 앞, 정리는 포기 검사 뒤.
  - 일일 상한은 작업 단위, 요청 수는 지연 리셋.
  - `openai`는 잔액을 보지 않는다.
  - 보류 진입마다 운영자 알림. `blocked`는 로그만.
- **정본이 정하지 않아 정한 것** (문서에 남긴다):
  - 게이트의 잔액 조회 실패는 통과, 해제 확인의 조회 실패는 계속 보류.
  - 보류 해제는 알리지 않는다.
  - 가짜 계획은 아직 요청을 세지 않는다. 계획 단계에서 실제 호출로 바뀌면 센다.
  - 통화 경고는 어댑터 단계로 미룬다.

## 구현 결과

계획한 커밋 단위대로 들어갔다. `pnpm check`는 테스트 243개로 통과한다. 달라진 점과 알아둘 점은 아래와 같다.

- **빠진 테스트 둘:**
  - `blocked` 중 정리 포기 알림: 보류 중에는 정리가 돌지 않아 이 상황에 닿을 수 없다. `blocked` 중 알림이 로그로만 남는 분기는 103(진입 알림)이 쓴다.
  - 계획 시도 횟수: 가짜 계획은 시도를 선기록하지 않아, 게이트를 선기록 앞에 두었는지 가려내지 못한다. 계획 단계에서 넣는다. 계획이 해제 뒤에 도는 것은 111과 111a가 본다.
    - 6단계에서 넣었다. [`plan.md`](plan.md).
- **"해제 뒤 같은 예약으로 개시"는 110에서 본다.** 일일 상한 보류는 자정에 풀리는데, 그때 날 넘김이 전날 예약을 지운다. 그래서 같은 날 풀리는 잔액 보류로 확인한다.
- **낮은 상한은 새 날에도 같다.** 87은 상한 1이라 해제 뒤 정리가 하루치 요청을 다 쓰고 계획은 다시 보류된다. 그래서 87은 정리까지만 본다. 109a는 상한 2로 두어 해제 뒤 판정과 계획이 모두 돈다.
- **87은 11.14 파일에 있다.** 정본에서는 11.11이지만 보류 테스트와 준비가 같다.
