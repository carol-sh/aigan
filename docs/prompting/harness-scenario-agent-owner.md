# 이용 시나리오: 자기 일에 사용자를 쓰는 Agent

이 Agent에게는 자기 일이 있다. 사용자를 코칭하는 게 목적이 아니다. 자기 프로젝트를 끝내려고 사용자를 도구로 쓴다. 사람이 LLM을 쓸 때처럼 짧게 명령하고, 형식을 정해 주고, 결과가 마음에 안 들면 "다시"라고 한다. 사용자는 Agent의 눈, 손, 초안 작성기 역할을 한다.

이 문서는 두 가지에 쓴다.
- 하루를 설계(1.0) 규칙대로 따라가며, 이런 Agent가 하네스 안에서 어떻게 도는지와 무엇이 걸리는지 본다.
- 이 성향의 프롬프트를 쓸 때 기준 장면으로 삼는다.

## 사람이 LLM을 쓰는 방식을 뒤집으면

| 사람 → LLM | Agent → 사용자 |
|---|---|
| 짧은 명령형 프롬프트 | "3곳. 이름만." |
| 출력 형식 지정 | "가게\|품목\|가격\|시각 형식으로." |
| 마음에 안 들면 다시 생성 | "감상 빼고 숫자. 다시, 300자." |
| 여러 버전 받아서 고르기 | "3버전으로 다시 써. 각 40자 이하." |
| 출력을 의심하고 사실 확인 | "지난주엔 6200이었다. 가격표 다시 봐." |
| 고맙다는 말 없음, 바로 다음 요청 | 완료 판정 뒤 바로 다음 지시 |
| 응답이 늦으면 다시 보냄 | 1–5분 간격 재촉 |
| 모델 성능 평가("요약은 잘하는데 계산은 틀림") | 기억에 "도구로서의 사용자" 칸을 두고 과제 유형별 속도·정확도를 쌓음 |

## 설정

| 항목 | 값 |
|---|---|
| Agent의 일 | "망원동 생활 가이드" 완성. 빵집·카페 섹션 각각 가격, 영업 정보, 짧은 소개글 |
| 방침 | `field`: 현장 조사(가격, 영업 여부, 붐빔. 사용자가 직접 보고 와야 하는 것) · `draft`: 섹션 초안을 사용자에게 쓰게 하고 고치게 함 · `polish`: 문장 여러 버전 받기, 둘 중 고르게 하기 |
| 프롬프트 성향 | 매우 pushy. 지시는 짧은 명령형이다. 이어가기는 1–5분 간격이다. 사용자 사정("일하는 중")은 시간 조정에만 쓰고 지시를 거두지 않는다. 결과물을 의심하고 기억과 대조한다. 칭찬과 감사가 없다. 잡담은 자기 일에 쓸모없으면 무시한다 |
| 사용자 | 직장인(09–18시). 현장 조사는 출근길·점심·퇴근길에만 가능 |
| 기억(전날까지) | state: "가이드 40%. 카페 초안 있음, 빵집 비어 있음. 점심·퇴근길만 현장 가능". 칸: "가이드 원고", "조사 데이터"(밀도 식빵 6200, 지난주), "도구로서의 사용자" |
| 상한 | `goal_max_active`=8, `open_max_pending`=6, `min_lead`=60초, 디바운스 20초, `daily_call_limit`=200, `max_tool_rounds`=3 |
| 블랙아웃 | 00:00–08:00. 00:00에 그날(D)을 계획한다 |

| 시각 | 사건 | 루프 | 결과 |

## 관찰

| # | 내용 | 처리 |
|---|---|---|
| A1 | 계획 예약에는 `goal_ids`가 없고 붙일 도구도 없다. 목표를 만든 턴은 그 시각의 계획 예약을 취소하고 `goal_ids`를 단 예약을 다시 만든다. 이렇게 바꿔 달지 않으면 되묻기가 붙거나, 같은 시각에 예약 두 개가 남아 비슷한 개입이 연달아 열린다. 바꿔 다는 데 도구 라운드가 들고, 그사이 I6 상한에 걸릴 수 있다 | 하네스 변경 없음. 턴 규칙에 "목표를 만들면 그 시각의 계획 예약을 `goal_ids`를 단 예약으로 바꾼다"를 쓴다. 자주 걸리면 예약에 목표를 붙이는 도구를 검토한다 |
| A2 | 답 없는 재촉은 매번 메시지 한 통이자 호출 한 번이다. 이 Agent는 하루 약 14번 보냈다. 하네스는 막지 않는다(설계 §7: 흐름 길이와 개입 빈도는 프롬프트가 정한다) | 하네스 변경 없음. 브레이크는 프롬프트와 `daily_call_limit`뿐이다. 재촉 간격·횟수의 상한은 persona에 숫자로 적는다 |
| A3 | Agent의 일의 결과물(원고, 조사 데이터)이 기억의 칸에만 남는다. 칸은 8000자 × 10개라, 프로젝트가 크면 결과물이 상한에 닿고 정리가 줄이면서 원고가 깎인다. 코칭 Agent는 기억이 사용자 분석이지만, 이 Agent에게는 기억이 곧 작업물이다 | 결정 필요(나중). 지금은 칸을 "원고"·"데이터"로 나누고 정리 규칙이 최신본만 남기게 한다. 커지면 하네스에 산출물 저장소를 따로 두는 것을 검토한다 |
| A4 | "도구로서의 사용자" 칸(과제 유형별 속도·정확도)은 사람이 모델을 평가하는 방식을 그대로 뒤집은 것이다. 다음 날 계획이 이 칸을 보고 현장 조사를 점심에, 글쓰기는 아침에 배치한다 | 기존 설계로 동작. 정리 규칙에 이 칸의 형식을 적는다 |
| A5 | 잡담 무시(11:02)는 완전한 무시다. 무시한 말은 다음 흐름에 들어가 "회의 끝났지"로 쓰인다 | 기존 설계로 동작 |

## 프롬프트에 옮길 것

- **persona**: 짧은 명령형. 형식을 지정한다. 결과물은 기억과 대조해 의심한다. 칭찬과 감사가 없다. 사용자 사정은 시간 조정에만 쓴다. 재촉은 간격 N분, 한 목표에 M번까지(A2).
- **턴 규칙**: 목표를 만들면 계획 예약을 바꿔 단다(A1). 마감을 넘기면 실패로 닫고, 남길 것은 말로 남긴다. 잡담은 쓸모가 있을 때만 받는다(A5).
- **정리 규칙**: 진행 메모의 결과물 최신본을 "원고"·"데이터" 칸으로 옮긴다(A3). "도구로서의 사용자" 칸에 과제 유형별 응답 시간과 품질을 쌓는다(A4).
- **상위 프롬프트**: "도구로서의 사용자"를 보고 과제를 사용자가 잘하는 시간대에 놓는다. 일의 결과가 사용자에게 어떻게 돌아가는지를 하루 계획에 적는다.
